# Midnight Aura Likes and Subscription specification

## Scope and sources of truth

DES-04 applies Midnight Aura Glass to incoming Likes and the existing
Subscription flow. It does not change backend code, HTTP contracts, Like or
Match semantics, Discovery, the current-user profile, Chats, onboarding,
registration, settings, package identity, or Android signing.

Backend OpenAPI and the implemented controllers remain the source of truth.
The Flutter flow uses only these existing endpoints:

```text
GET  /likes/liked_me
GET  /likes/liked_users
GET  /likes/favorites
POST /likes/like/{user_id}

GET  /user/{user_id}
GET  /user/user/photos/{user_id}

GET  /subscriptions
GET  /subscriptions/active
POST /subscriptions/checkout
GET  /subscriptions/payments/{order_id}
POST /subscriptions/demo/payments/{order_id}/{success|failure}  (demo only)
```

The client never calls `/subscriptions/init_payment`, a T-Bank endpoint, or a
bank webhook. The canonical checkout request contains only
`subscription_id`; its `Idempotency-Key` is generated by the client. Price,
order identifiers, payment status, bank Token, terminal credentials, RebillId,
and subscription activation remain backend responsibilities.

## Contract reality: Likes

All three Likes list endpoints currently return complete JSON arrays and have
no pagination or count parameters. Flutter must not create fake pagination on
top of those arrays. The incoming-like count is therefore the length of the
real, deduplicated `liked_me` response.

The current `UserLikesResponse` can provide:

- real user `id`;
- optional `first_name`;
- optional `date_of_birth`, from which age is derived locally;
- optional `city_name`;
- optional `about_me`;
- optional `avatar_url`;
- optional `mutual`;
- optional `status`, `is_favorite`, `match_percentage`, and attributes.

The redesigned grid renders only id, first name, derived age, city, real
avatar, and mutual state where relevant. It deliberately omits `status` and
`match_percentage`, because neither is a reliable presentation contract.
Verified state and distance are not returned by the Likes contract and are not
invented. No static profiles, generated photos, compatibility scores, online
badges, interests, or counters are added.

The backend currently returns the same Likes payload regardless of active
subscription. Premium gating is therefore a Flutter presentation/access
decision backed by a separate `GET /subscriptions/active` check. Locked
personal text is excluded from semantics and interaction; only the real count
and obscured real media may be shown.

## Contract reality: premium access

`GET /subscriptions/active` always returns either:

```json
{"subscription": null}
```

or a real active subscription with id, name, start/end timestamps, and
`renewable` metadata. It is the access source of truth. The current-profile
`is_subscription` value may be refreshed after activation for compatibility,
but it does not replace the active-subscription request.

Access has explicit unresolved, loading, inactive, active, and error states.
Until the first backend access result is known, Likes shows a stable skeleton
and never flashes unlocked content. A previously confirmed active value may be
retained during a background refresh to avoid a false locked flash.

## Likes information architecture

The existing four real datasets remain available without changing product
semantics:

```text
Liked me   -> premium-gated incoming likes
My likes   -> users liked by the current user
Favorites  -> existing favorites
Matches    -> real records whose mutual field is true
```

The default and primary experience is `Liked me`:

```text
static Midnight Aura backdrop
-> one compact LikesTopBar with real incoming count when loaded
-> compact category control
-> lazy profile grid
-> premium gate only for incoming likes when access is inactive
-> existing floating shell navigation
```

All categories reuse a two-column `LikesProfileGrid` on a normal phone. The
grid adapts spacing and column count for compact and wide layouts, uses stable
user-id keys, bounded media with `BoxFit.cover`, Flutter image caching, a
deterministic loading placeholder, and the branded missing/broken-image state.
Cards are solid/translucent surfaces and never contain `BackdropFilter`.

## Locked Likes

If access is confirmed inactive and real incoming Likes exist, the grid shows
only obscured real media behind one non-manipulative premium explanation:

```text
See who already likes you
-> View plans
```

Names, ages, cities, mutual state, and image semantics are unavailable to
screen readers and pointer interaction while locked. The count remains real.
The UI does not fabricate demand when the incoming list is empty; it shows an
honest empty state and no fake cards or count. An inactive user may still open
the real Premium plans from that state, alongside the route back to Discovery.

The premium overlay is solid/translucent rather than another blur region. The
entire locked media layer may use one bounded foreground image filter; it does
not create a `BackdropFilter` per profile. There are no scarcity messages,
discount timers, popularity claims, or invented benefits.

## Unlocked Likes and Like back

With a confirmed active subscription, incoming cards expose real photos and
available identity fields. Selecting a card opens the existing public-profile
route with the real user id; the route still refreshes complete profile details
and photos through the canonical profile endpoints.

The public profile delegates Like back to the existing Discovery reaction
controller/repository and uses the existing `/likes/like/{id}` semantics. A
successful reaction removes the processed incoming card from local Likes state
and refresh no longer presents an already-mutual card as an unprocessed Like.
A mutual result opens the existing Match route and existing Match screen. Chat
creation/reuse continues through `ChatListController.openOrCreate`; no second
Match or Chat flow is introduced.

## Likes state matrix

| State | Presentation | Action |
| --- | --- | --- |
| access unresolved/loading | stable two-column skeleton | Back/navigation |
| Likes loading | stable two-column skeleton | navigation |
| inactive + incoming data | obscured real grid and premium gate | View plans |
| active + incoming data | real lazy grid | open profile |
| empty incoming | honest `New likes will appear here` state | Discover / View plans when inactive |
| initial error | solid safe error state | Retry |
| refresh error with data | retained content and compact live-region error | Retry |
| missing/broken image | branded bounded placeholder | normal valid action |

Refreshing Likes refreshes both real Likes data and premium access. It does not
clear the selected category or scroll state unnecessarily.

## Contract reality: plans and checkout

`GET /subscriptions` returns active plans with:

- `id`;
- `name`;
- optional `description`;
- integer `price_minor`;
- `currency` (currently RUB);
- `duration_days`;
- `is_active`;
- `renewable` metadata.

There is no preferred/default/popular/discount field. Flutter selects the
first valid active plan when no prior valid selection exists and never labels a
plan as best, popular, discounted, or scarce. Price is formatted only for
display from backend minor units and is never sent back as authoritative data.
Period copy derives from `duration_days`; it is not converted into an invented
billing promise.

Automatic recurrent charging is outside the current product stage and backend
configuration uses `TBANK_RECURRENT_ENABLED=false`. The returned `renewable`
field is metadata only. DES-04 therefore shows no auto-renew management,
cancel-renewal button, recurring promise, or fake billing settings even if a
fixture returns `renewable=true`.

## Subscription structure

```text
static Midnight Aura backdrop
-> one compact top bar with Back and optional real demo label
-> restrained SubscriptionHero
-> real plan options on solid surfaces
-> one selected plan
-> contextual status panel
-> canonical SubscriptionCheckoutButton
-> payment/security explanation
```

`SubscriptionPlanCard` supports selected, unselected, disabled, and loading
states. Selection is conveyed by semantics, radio icon, border, and copy rather
than colour alone. Long names, descriptions, prices, 1.3 text scale, and a
320 x 568 logical viewport wrap or scroll without overflow. All controls meet
the 48 logical-pixel target.

## Checkout and return flow

The only creation path is:

```text
POST /subscriptions/checkout
-> validate absolute backend PaymentURL
-> launch external application
-> await backend confirmation
```

State changes synchronously to creating before the first await, so repeated
taps cannot create another checkout. The same generated idempotency key is used
for that request. If external launch fails after checkout creation, Retry
reopens the stored URL instead of creating a second checkout.

The application currently has no dedicated app-link/deep-link payment handler.
Its established return mechanisms are lifecycle `resumed`, bounded polling,
and manual status refresh. DES-04 preserves that architecture instead of adding
a parallel callback. Resume and Retry call only:

```text
GET /subscriptions/payments/{order_id}
```

A browser return is never treated as success. The verifying view is bounded,
allows Back and Retry, and retains the selected plan and checkout. Pending,
requires-action, and processing remain non-success states. Failed, canceled,
refunded, and partially refunded receive explicit terminal presentation without
activating access.

`succeeded` unlocks Likes only when backend also confirms subscription
activation and supplies, or subsequently returns, a real active subscription.
The controller then refreshes the existing current-profile state for
compatibility. Reopening the app calls `/subscriptions/active`, so confirmed
access survives process restart. Recovery of an unconfirmed order after a full
process death is not possible with the current API because there is no endpoint
that lists the user's pending checkouts.

## Demo flow

Demo uses the same canonical checkout DTO and state machine. The backend
returns a demo PaymentURL and exposes the existing protected demo-only result
endpoint. Explicit Demo success/failure controls call that backend endpoint,
then perform the normal payment-status verification. Flutter never fabricates
an activated subscription locally.

## Subscription state matrix

Plans, access, and checkout use separate state axes so an error in one does not
erase successful data from another.

| State | Presentation | Action |
| --- | --- | --- |
| plans loading | stable plan skeletons | Back |
| plans data | real plan cards and selected plan | select/checkout |
| plans empty | honest unavailable state | Retry/Back |
| plans error | safe error state, no fake plans | Retry/Back |
| creating checkout | fixed loading CTA | Back |
| launch error | stored-checkout error panel | Reopen payment/Back |
| awaiting/pending | calm pending panel | Check status/Back |
| verifying | `Checking subscription status` | Back |
| verification error | retained checkout and selection | Retry/Back |
| failed/canceled/refunded | explicit non-active panel | start new checkout |
| timed out | delayed confirmation panel | Check status/Back |
| active | active plan/name/end date when real | View Likes/Back |

## Routing

```text
Likes -> push /premium
/premium Back -> previous Likes context
/premium -> external checkout
lifecycle resume -> backend verification
active -> pop/go to /likes with unlocked provider state
Likes -> push /discover/profile/{real_id}?source=likes
Like back -> existing Match route on mutual result
Match -> existing real Chat route
```

There remains one Subscription route, one public-profile route, one Match
route, and one Chat route. The shell navigation is not duplicated. Subscription
is outside the tab shell so its Back action restores the selected Likes branch.

## Accessibility and effect budget

- System text scaling remains enabled and is tested at 1.3.
- High contrast strengthens card borders and selected/status indicators.
- Reduced motion requires no alternative because these screens add no looping
  or state-independent animations.
- Locked media is excluded from semantics; the gate exposes one concise label
  and action.
- Focus order follows top bar, category/count, content, primary action, then
  shell navigation; Subscription follows Back, value, plans, status, checkout.
- Selection and status never rely on colour alone.
- All icon and button targets are at least 48 x 48 logical pixels.

Visible `BackdropFilter` budget:

- Likes: one top bar plus the existing shell navigation; zero in grid cards;
- Subscription: one top bar; zero in plan/status cards.

Both screens use a static backdrop with no full-screen ticker. The Likes grid
is lazy, image bounds are stable, and remote raster images use Flutter's image
cache. Profile mode must inspect grid scrolling, first decode, locked overlay,
plan selection, external return, verification, and unlock.

## Test contract

Likes unit/widget coverage includes access loading, locked/unlocked data, real
count and no-count state, loading, empty, error/retry, missing image, long name,
Subscription navigation, active unlock, public-profile navigation, Like back,
mutual Match handoff, processed-card removal, no hardcoded profiles/counts,
text scale 1.3, compact viewport, semantics, and effect budget.

Subscription coverage includes plans loading/data/empty/error/retry, default
and changed selection, long plan content, disabled/loading checkout, double-tap
protection, canonical request, launch failure and URL reuse, lifecycle resume,
verifying/pending/failed/active/error/retry states, active presentation,
recurrent controls absent, no legacy/direct-bank request, Back, text scale 1.3,
and compact viewport.

The integration widget flow is:

```text
locked Likes -> Subscription -> select real fixture plan
-> canonical checkout -> simulated return -> backend fixture active
-> unlocked Likes -> public profile -> Like back -> existing Match -> Chat
```

Deterministic, animation-disabled goldens cover locked, unlocked, loading,
empty, error, and missing-image Likes plus plans, selected plan, loading,
checkout error, verifying, pending, active, and verification-error
Subscription. Production contains no golden-only profiles or fake payment
success.

## Known contract limitations

- Likes arrays are not paginated; only lazy rendering can be optimized today.
- Premium enforcement is not present in the Likes endpoint itself, so the
  backend still transports real Likes data to an inactive client.
- No dedicated payment-return deep link exists; resume/manual refresh are the
  available mechanisms.
- A pending checkout cannot be recovered after full process death without a
  backend list/recovery endpoint.
- `renewable` does not communicate the global recurrent feature flag, so the
  client intentionally exposes no recurring controls in this stage.
